# Strict-STM32

> **面向 AI 辅助开发的 STM32 强约束工作流**
> 
> 本项目提供了一套用于引导大语言模型（LLM）进行 STM32 嵌入式开发的行为约束规范。其核心设计思想是通过“强制读取真值、双向确认决策、实时维护日志”的机制，减少 AI 在寄存器配置、引脚复用及外设初始化时可能出现的幻觉与偏差。
> 
> *注：AI 自动执行的具体工作流请参考 `SKILL.md`，详细规则及方法论位于 `references/` 目录。*

---

## 📌 设计背景与解决痛点

在利用 AI 进行 STM32 开发时，由于不同系列芯片的寄存器定义、引脚复用（AF）以及时钟树配置存在差异，AI 容易出现以下共性问题：

- **基于不准确记忆生成代码**：生成错误的寄存器位定义或引脚复用编号。
- **时钟与外设使能遗漏**：漏调 `__HAL_RCC_GPIOx_CLK_ENABLE()` 等关键使能宏。
- **配置默认值不合预期**：在未明确应用场景的前提下，盲目采用默认参数（如默认波特率、校验位等）。
- **软硬件状态不同步**：硬件引脚或外设变动后，未能及时同步修改驱动代码与项目文档。

**Strict-STM32 工作流通过以下方式应对上述问题：**
1. **强制真值校验**：在编写或修改驱动前，强制 AI 检索工程实际引用的 HAL/CMSIS 头文件。
2. **决策前置确认**：定义必问清单，关键外设配置与业务决策必须由人工确认，避免 AI 自行假设。
3. **真相源同步**：每次硬件变动强制同步至 `HARDWARE.md`，保持文档与代码的一致性。

## 🛠️ 项目初始化与日常工作流

### 1. 项目初始化（首次使用）

1. 打开 **STM32CubeMX**，选择对应 MCU 并配置时钟树。
2. **关键设置**：Toolchain / IDE 选择 **CMake**（生成 CMake 预设和工具链文件）。
3. **关键设置**：勾选 **"Copy all library files into the project folder"**（将 HAL 库完整复制到工程中，作为 AI 的真值参考源）。
4. 将工程生成路径设为 `<project_root>/code/`。
5. 提示 AI 执行：“初始化 STM32 项目”。AI 将自动建立目录骨架，并生成 `HARDWARE.md` 和 `PROJECT.md` 模板。

### 2. 日常迭代步骤

在开发新功能（例如“添加 MPU6050 驱动”、“配置 USART3 收发”）时，AI 将严格遵循 10 步迭代流程：

```
[阅读 HAL/CMSIS 头文件真值] ──> [用户确认决策] ──> [编写/修改代码]
                                                      │
[任务日志同步] <── [硬件文档同步] <── [自动编译验证] <──┘
```

#### 💡 渐进式验证原则（Baby Steps）
推荐采取分步验证的开发节奏，以降低调试复杂度：
1. **第一步**：通过读取芯片 ID（如 `WHO_AM_I` 寄存器）验证物理总线连通性。
2. **第二步**：实现基础的单次读写与配置唤醒。
3. **第三步**：引入中断、DMA 或复杂业务逻辑。

## 📂 目录与工程结构

本规范推荐的工程目录结构如下：

```text
project_root/                       # 宿主机工作目录
├── .claude/                        # Claude / AI 助手配置目录（Skill 逻辑存放处）
└── code/                           # STM32CubeMX 工程根目录 (VSCode 工作区根目录)
    ├── Core/                       # CubeMX 生成的主程序入口 (AI 仅修改 USER CODE 段)
    ├── Drivers/                    # HAL/CMSIS 库源码 (AI 只读，作为真值源)
    ├── driver/                     # MCU 内部外设驱动层 (如 driver_i2c.c)
    ├── bsp/                        # 外部板级芯片驱动层 (如 bsp_mpu6050.c)
    ├── middleware/                 # 中间件层：纯软件逻辑 (不依赖硬件)
    │   ├── protocol/               # 报文切帧、CRC 校验、Modbus/自定义协议解包
    │   └── utils/                  # RingBuffer、FIFO、CRC 算法、调试日志
    ├── app/                        # 纯业务逻辑层 (不直接依赖具体硬件句柄)
    ├── sandbox/                    # 临时脚手架/验证代码存放区 (验证后可清理)
    ├── hw/
    │   └── datasheets/             # 外部芯片的 Datasheet PDF 存放区
    ├── HARDWARE.md                 # 硬件配置真相源 (引脚、外设参数)
    ├── PROJECT.md                  # 项目阶段目标与路线图
    └── tasks/                      # 任务级开发与决策日志
```

### 四层解耦架构说明

为实现代码的清晰边界与高复用性，工程采用单向依赖的四层架构：

```
┌──────────────────────────────────────────────┐
│                  app/ 应用层                  │ (业务逻辑/状态机，只消费 Middleware 输出的 Struct)
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│             middleware/ 中间件层              │ (协议切帧/CRC/数据结构/算法，纯逻辑、不依赖硬件)
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│                  bsp/ 板级层                 │ (实现传感器/外设芯片驱动，使用 driver 接口)
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│                driver/ 驱动层                │ (封装 MCU 内部外设，直接调用 HAL/LL 库)
└──────────────────────────────────────────────┘
```
- **Middleware 纯逻辑**：`middleware/` 层只做数据转换（接收 Byte、输出 Struct），严禁触碰 HAL 句柄、外设寄存器或业务逻辑，严禁包含任何 `app_*.h` 头文件。
- **共享外设单例模式**：例如多个 BSP 芯片（如 MPU6050 和 OLED）共用同一条 I2C 总线时，BSP 层严禁直接操作全局 `hi2c1` 句柄，必须通过 `driver_i2c_*` API 读写，避免资源冲突。

## 🛡️ 13 条强制行为准则 (Strict Rules)

| 规则 ID | 规则名称 | 核心要求描述 |
|---|---|---|
| **SR1** | **宏定义安全** | 修改 `stm32f4xx_hal_conf.h` 等配置文件时，仅允许修改 `MODULE_ENABLED` 相关的宏。 |
| **SR2** | **外设修改冻结** | 禁止直接在 STM32CubeMX 中任意更改已配置好的外设逻辑，防止覆盖手写代码。 |
| **SR3** | **时钟配置冻结** | 严禁手动修改 `SystemClock_Config()` 里的时钟倍频/分频系数。 |
| **SR4** | **真值检索先行** | 编写 `driver` 或 `bsp` 代码前，必须先检索并阅读对应的 HAL/CMSIS 头文件（middleware 除外：纯逻辑层，真值源是协议/帧格式定义，不读 HAL）。 |
| **SR5** | **禁止跨层调用** | `bsp/` 层的驱动代码严禁直接读写外设硬件句柄，必须通过 `driver` 层提供的 API 传输。 |
| **SR6** | **单向包含依赖** | 头文件包含关系只能自上而下（`app` ➔ `middleware` ➔ `bsp` ➔ `driver`），禁止逆向或环形依赖。 |
| **SR7** | **真相源同步** | 任何硬件引脚、总线或关键时序变动，必须同步更新至 `HARDWARE.md`。 |
| **SR8** | **CMake 重载** | 增加、删除或重命名 `.c` 源文件后，必须重新配置并生成 CMake 缓存。 |
| **SR9** | **反盲目决策** | 凡涉及缺失参数或临界配置，必须询问用户决策，严禁 AI 默认代劳。 |
| **SR10** | **数据手册优先** | 集成冷门或非标准外设芯片时，必须查阅相关 Datasheet 规范，严禁凭经验盲写。 |
| **SR11** | **变量命名规范** | 禁止使用不具备业务含义的泛化变量名（如 `temp`, `flag`, `data`, `count` 等）。 |
| **SR12** | **注释规范** | 头文件注释重点说明“是什么/做什么”，源文件内部注释重点解释“为什么这样设计/特殊时序说明”。 |
| **SR13** | **架构完整性** | 项目初始化阶段必须完整建立 `app/`、`bsp/`、`middleware/`（含 `protocol/` `utils/` 子目录）、`driver/` 四层目录（即使某些目录暂时为空）。 |

## 📂 规则库与模板说明

本仓库包含以下组件，您可以根据需要将其配置到您的 AI 助手中：

- **`SKILL.md`**：AI 读取的执行主流程规范，详细定义了 10 步分析法。
- **`references/`**：包含架构设计、反幻觉校验、CMake 集成、验证步骤以及演进流程的详细文档。
- **`assets/`**：提供 `HARDWARE.md`、`PROJECT.md` 和任务日志的标准化模板，以便开箱即用。
