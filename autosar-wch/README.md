# AUTOSAR-WCH 架构开发规范与项目模板

本规范与模板旨在为 WCH RISC-V MCU（如 CH32V307 等系列）在 MounRiver Studio 环境下的开发提供一套清晰的三层解耦架构设计标准。

其核心设计吸收了 AUTOSAR 的分层思想，并结合了 John Ousterhout 的《软件设计哲学》（*A Philosophy of Software Design*），重点解决嵌入式开发中常见的硬件依赖深、代码耦合度高、时序逻辑混乱等问题。

---

## 🏗️ 核心架构：三层解耦模型

本项目严格限制代码的依赖关系，只允许**单向依赖**：`App (应用) -> Bsp (板级支持) -> Mcal (芯片抽象)`。严禁跨层调用或反向依赖。

```
+-------------------------------------------------------------+
|                     User/main.c (组合根)                    |
+-------------------------------------------------------------+
                               | (系统装配与驱动)
                               v
+-------------------------------------------------------------+
| App 层 (应用业务逻辑)                                        |
| - 纯粹的控制算法与业务状态机                                 |
| - 与硬件无关，被动接受 Delta Time 驱动                      |
+-------------------------------------------------------------+
                               | (物理抽象调用)
                               v
+-------------------------------------------------------------+
| Bsp 层 (板级支持包)                                         |
| - 驱动外部器件 (如传感器、显示屏、执行器)                     |
| - 将底层通信抽象为物理世界概念（如摄氏度、百分比）            |
+-------------------------------------------------------------+
                               | (寄存器与外设调用)
                               v
+-------------------------------------------------------------+
| Mcal 层 (微控制器抽象层)                                     |
| - 屏蔽 MCU 寄存器与固件库细节（如 GPIO, USART, ADC）         |
| - 实现中断闭环与状态维护                                     |
+-------------------------------------------------------------+
```

### 1. User/main.c（组合根）
- **初始化阶段**：负责跨层调用各层的初始化函数（如 `Mcal_Init()`、`Bsp_Init()`、`App_Init()`）完成依赖注入。
- **运行阶段**：在 `while(1)` 中计算系统时间步长（Delta Time），并将其传递给 App 层（如 `App_Run(dt_ms)`）。主循环中不应包含具体的业务逻辑。

### 2. App（应用层）
- 仅关注业务逻辑，**禁止引入任何硬件头文件**。
- 不得使用任何硬件阻塞延时（如 `Delay_Ms`），所有时间相关的逻辑均由外部传入的 Delta Time 驱动。

### 3. Bsp（板级支持包）
- 消化器件的物理地址、通信时序与忙等待。
- **禁止透传**：Bsp 接口不能是 Mcal 接口的简单封装，而应当提供具有物理意义的抽象（例如 `Bsp_TempSensor_GetCelsius()`，而非 `Bsp_Read_I2C_Register()`）。

### 4. Mcal（微控制器抽象层）
- 屏蔽芯片特定的寄存器与外设库细节。
- **中断跳板机制**：`ch32v30x_it.c` 中的中断服务函数仅作为无脑“跳板”，直接转发给 Mcal 的相应中断处理函数，硬件标志位的清除与维护在 Mcal 内部闭环。

## 📁 目录结构规范

在使用 MounRiver Studio 创建的项目中，物理目录结构需保持如下规范：

```
├── User/             # 组合根：main.c, ch32v30x_it.c (中断跳板)
├── App/              # 应用层：业务控制逻辑 (.c/.h)
├── Bsp/              # 板级支持包：外部传感器、执行器驱动 (.c/.h)
├── Mcal/             # 芯片抽象层：串口、定时器、ADC 等芯片外设封装 (.c/.h)
|
# 以下为 WCH 官方底座目录，严禁破坏、删除或移动
├── Core/             
├── Debug/            
├── Ld/               
├── Peripheral/       
└── Startup/          
```

## ✍️ 编码与注释规范

为了提高代码的可读性与维护性，项目开发中需遵循以下代码哲学：

### 1. 窄命名原则 (Narrow Names)
避免使用无具体物理或业务意义的泛化变量名：
- 禁用：`temp`、`flag`、`data`、`count`、`val`。
- 启用：`current_celsius`（当前摄氏度）、`bus_busy_flag`（总线忙标志）、`uart_rx_byte_count`（串口接收字节数）。

### 2. 奥斯特豪特注释原则 (What & Why)
- **头文件 (.h) —— 关注 "What"（接口契约）**：
  说明该接口“做什么”以及“如何使用”，**严禁泄露底层实现细节**。
  ```c
  // 推荐：获取当前空气的物理温度。若传感器掉线，函数将返回上一次读取的有效值。
  float Bsp_TempSensor_GetCelsius(void);
  ```
- **源文件 (.c) —— 关注 "Why"（设计意图）**：
  解释代码背后不明显的逻辑决策、硬件限制或规避措施，**严禁逐行翻译代码的实现过程**。
  ```c
  // 硬件设计限制：在外设启动前需要等待至少 2ms 确保电荷泵电容稳定充电
  Mcal_GPIO_WriteBit(GPIO_PIN_0, BIT_RESET);
  ```

### 3. 在底层消化异常
硬件层面的错误（如通信超时、数据校验失败）应在 Mcal 或 Bsp 层内部进行消化和复位尝试。Bsp 层应向 App 层输出安全的默认值或保持上一帧有效值，避免将硬件物理故障扩散至应用层算法。

## 🚀 如何在项目中使用

1. **导入模板**：在 MounRiver Studio 中保留底座目录，并在根目录下新建 `App/`、`Bsp/`、`Mcal/` 文件夹。
2. **定义接口契约**：在编写具体实现前，先在各自层的 `.h` 文件中定义好接口与注释。
3. **集成业务**：在 `User/main.c` 中配置时钟与外设，在主循环中通过时间片或 Delta Time 驱动 `App_Run()`。
