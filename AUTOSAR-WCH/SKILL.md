# AUTOSAR-WCH Architecture Guide

激活关键词：`设计功能`、`重构代码`、`创建新模块`、`WCH架构`、`App Bsp Mcal`、`三层架构`

---

## 运行准则

1. **主动引导**：用户在 MounRiver Studio 下开发 WCH RISC-V MCU 项目时，以此规范作为架构决策的唯一标准。
2. **三层解耦 (App -> Bsp -> Mcal)**：严禁跨越层级调用或反向依赖。
3. **目录物理结构不可侵犯**：`Core`、`Debug`、`Ld`、`Peripheral`、`Startup`、`User` 目录**严禁破坏、删除或移动**。
4. **组合根模式**：`User/main.c` 仅负责系统装配与主循环节拍，App 层以被动驱动方式接受 Delta Time。
5. **Ousterhout 命名与注释原则**：窄名字 (Narrow Names)、What/Why 而非 How、信息隐藏。

---

## 架构分层规范

### 1. User/main.c - 组合根 (Composition Root)

**Setup Phase（初始化阶段）**：
- 允许跨层调用 `Mcal_Init()`、`Bsp_Init()`、`App_Init()` 进行系统装配与依赖注入。

**Run Phase（运行阶段）**：
- 在 `while(1)` 循环中，**仅允许**调用 `App` 层的运行时接口。
- 计算或提供系统时间步长（Delta Time），注入给 App（例如 `App_Run(uint32_t dt_ms)`）。
- **严禁**在 App 层调用任何硬件延时函数（如 `Delay_Ms`）。

### 2. App（应用层）

- 职责：纯粹的业务控制逻辑和核心算法。
- **铁律**：不允许包含任何硬件头文件或通信协议细节。
- App 必须是时间与硬件双重解耦的被动驱动体。

### 3. Bsp（板级支持包）

- 职责：将底层的通信和 IO 转化为"物理世界"的抽象（如获取摄氏度、设置百分比占空比）。
- **严禁透传 (No Pass-through Methods)**：Bsp 绝不能是 Mcal 接口的简单套壳。
- Bsp 必须在内部消化器件物理地址、命令时序、忙等待等。

### 4. Mcal（微控制器抽象层）

- 职责：屏蔽芯片寄存器与固件库细节。
- **中断跳板规则 (Trampoline ISR)**：`User/ch32v30x_it.c` 仅作为中断的无脑"跳板"，直接转发给 Mcal（如 `Mcal_UART1_IRQHandler()`）。所有标志位清除、硬件状态机维护必须在 Mcal 内部闭环。
- **深度初始化**：Mcal 初始化函数必须自动处理时钟使能、复用功能（AFIO）等，对外仅暴露极简参数。

## 精密命名规范

1. **严禁浅名字 (Vague Names)**：
   - 绝对禁止：`data`、`status`、`val`、`temp`（易与温度/临时变量混淆）、`res`、`flag`、`count`、`len` 等。

2. **必须使用窄名字 (Narrow Names)**：
   - 用 `bus_busy_flag` 代替 `flag`；用 `current_celsius` 代替 `temp`；用 `retry_count` 代替 `count`；用 `uart_rx_byte_count` 代替 `len`。

3. **保持全局一致性**：
   - 相同的概念在整个项目中必须使用相同的业务词汇。若使用 `celsius` 表示摄氏度，则绝不能在其他地方混用 `temperature_f` 或 `t`。

## 奥斯特豪特注释规范

### 头文件 (.h) 接口注释：只关注 "What"

- 头文件是对外暴露的"接口契约"，只能注释：
  - "做了什么（What）"
  - "如何正确使用（用法、前置条件、返回值意义）"
  - **绝对不能泄漏"如何实现（How）"**

❌ **红色警告（信息泄漏）**：
```c
// 本函数通过 I2C 寻址 0x3C 并读取寄存器 0x01 来获取温度值。
```

✅ **绿色合规（抽象契约）**：
```c
// 获取当前空气的物理温度。若传感器掉线，函数将返回上一次读取的有效值，防止上层算法失控。
```

### 源文件 (.c) 实现注释：关注 "Why" 与高层 "What"

- 绝对禁止逐行翻译代码的"How"。
- **解释 "Why"**：解释代码背后不明显的逻辑决策、设计考量、硬件限制或变通方案（Workarounds）。

❌ **红色警告**：
```c
I2C_GenerateSTART(I2C1, ENABLE); // 开启I2C1起始信号
```

✅ **绿色合规**：
```c
// 硬件设计缺陷：在外设启动前需要等待至少 2ms 确保电荷泵电容稳定充电
```

- **解释高层级的 "What"**：在复杂的代码块或循环前，用一两句话描述这一整段代码在概念上是在"干什么"。

### 通过定义规避错误 (Define Errors Out of Existence)

- 硬件通信错误必须在 Mcal/Bsp 层内部消化并复位。
- 若硬件失效，Bsp 应提供合理的默认安全值或锁存上一帧有效值，确保 App 层的控制算法保持逻辑纯粹、不受硬件故障干扰。

## 执行动作

当用户要求"设计功能"、"重构代码"或"创建新模块"时，必须严格遵守以下步骤：

### 1. 审视架构边界

- 指出该功能涉及哪些层（App/Bsp/Mcal）。
- 各层的抽象应该是什么。

### 2. 操作文件系统

- 直接使用文件系统工具在 `App/`、`Bsp/`、`Mcal/` 目录下创建必要的文件夹、`.c` 和 `.h` 骨架文件。

### 3. 隔离时间与硬件依赖

- 确保 App 层不包含延时函数。
- 设计为被动接受 Delta Time 驱动。

### 4. 严格审查命名与注释

- 检查生成的头文件和源文件。
- 消除万能变量名。
- 确保注释符合"What & Why"原则。
- 彻底杜绝废话注释与接口信息泄漏。

```
User/           - 组合根（main.c + 中断跳板）
App/            - 应用层（业务逻辑）
Bsp/            - 板级支持包（物理抽象）
Mcal/           - 微控制器抽象层（寄存器屏蔽）

⚠️ 严禁破坏以下目录：Core、Debug、Ld、Peripheral、Startup
```
